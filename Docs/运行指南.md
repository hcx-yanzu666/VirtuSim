# 运行一次仓库导航

本文用于日常重新启动项目。Ubuntu 文件部署见 [ROS2 工具说明](../Tools/ROS2/README.md)，问题排查见 [ROS2 与 Nav2 排查](Troubleshooting/ROS2与Nav2排查.md)。

## 1. 环境与文件准备

| 位置 | 当前约定 |
|---|---|
| Windows | UE 5.6，`VirtuSim.uproject`，TempoROS 与 UMGAutoBuilder 插件 |
| Ubuntu | VMware 虚拟机，ROS2 Humble、Nav2、RViz2 |
| ROS 工作目录 | `/home/ros2/virtusim_nav2` |
| Nav2 参数 | `params/nav2_params_full.yaml`，沿用已联调版本 |
| 地图 | `maps/warehouse_map.yaml` 与同目录 PGM |
| Bridge | `scripts/goal_bridge.py` |
| 诊断 | `scripts/virtusim_nav_diagnostics.py` |

仓库的 [旧参数基线](../Tools/ROS2/params/README.md) 不是当前完整运行配置；[地图快照](../Tools/ROS2/maps/README.md) 也需要确认与关卡匹配。不要仅因目录整理就覆盖 Ubuntu 已调好的文件。

每个 Ubuntu 新终端先执行：

```bash
source /opt/ros/humble/setup.bash
export ROS_DOMAIN_ID=0
unset ROS_LOCALHOST_ONLY
```

Windows UE 与 Ubuntu 需要能通过 DDS 通信，ROS Domain 一致；确认 VMware 网络与防火墙允许对应网络通信。

## 2. Windows：打开 UE 测试地图

1. 使用已有构建环境编译并打开 `VirtuSim.uproject`。
2. 在内容浏览器打开 `LidarTestMap`；当前 `DefaultEngine.ini` 的默认地图不是该测试地图。
3. 检查 SFL_CBD16 机器人、仓库和 LiDAR 参数，确认选用地图与 ROS 静态地图一致。
4. 首次恢复环境先做手动导航；若关卡内启用了 `ScenarioRunner`，注意它会在 `BeginPlay` 自动发送目标。
5. 点击 Play。UE 曾在失焦时降频，测试期间检查后台限帧或编辑器的后台 CPU 限制。

## 3. Ubuntu：确认 UE 发布

在准备好环境变量的终端执行：

```bash
ros2 topic list -t
timeout 10s ros2 topic hz /clock
timeout 10s ros2 topic hz /scan
timeout 10s ros2 topic hz /odom
```

上述命令依次运行，每条最长 10 秒。默认扫描参数为 10 Hz，里程计目标约 30 Hz；以当前 UI 和实际帧率为准。

TF 应为 `map → odom → base_link → laser_link`。当前 UE 发布固定 `map → odom`，Nav2 参数中的 AMCL 不应重复广播该变换。

## 4. Ubuntu：启动 Nav2

新开终端，执行本页环境初始化命令后运行：

```bash
ros2 launch nav2_bringup bringup_launch.py \
  map:=/home/ros2/virtusim_nav2/maps/warehouse_map.yaml \
  params_file:=/home/ros2/virtusim_nav2/params/nav2_params_full.yaml \
  use_sim_time:=true
```

在另一个已初始化终端确认：

```bash
ros2 lifecycle get /planner_server
ros2 lifecycle get /controller_server
ros2 lifecycle get /bt_navigator
ros2 action info /navigate_to_pose
```

导航生命周期节点应为 `active [3]`，Action 应存在可用 Server。

## 5. Ubuntu：启动 Bridge、RViz 和诊断

分别在三个新终端执行环境初始化，再运行以下命令；每个进程占用一个终端。

Bridge：

```bash
python3 /home/ros2/virtusim_nav2/scripts/goal_bridge.py
```

只保留一个 Bridge 实例。

RViz：

```bash
rviz2 --ros-args -p use_sim_time:=true
```

RViz 中设置：

| 显示项 | 配置 |
|---|---|
| Fixed Frame | `map` |
| Map | `/map` |
| LaserScan | `/scan` |
| Path | `/plan` |
| TF | 启用 |
| Local / Global Costmap | `/local_costmap/costmap`、`/global_costmap/costmap` |

诊断使用独立文件，避免多次实验日志混在一起：

```bash
mkdir -p /home/ros2/virtusim_nav2/logs
python3 /home/ros2/virtusim_nav2/scripts/virtusim_nav_diagnostics.py \
  --output "/home/ros2/virtusim_nav2/logs/navigation_$(date +%Y%m%d_%H%M%S).jsonl"
```

## 6. 发出目标并验证

从 UE 界面发出目标，观察：

- Bridge 收到目标，Nav2 接受后 UE 状态进入 `Navigating`。
- RViz 地图、扫描和机器人位置对齐。
- `/plan` 更新，`/cmd_vel` 驱动 UE 位姿改变，odom / TF 随之更新。
- 到达后回传 `Succeeded`；取消操作应最终回传 `Canceled`，`Canceling` 只是过程状态。

必要时在额外终端查看：

```bash
ros2 topic echo /virtusim/navigation_status
```

若从 RViz 直接发送 Nav2 Action，可能绕过本项目 Bridge 的目标 / 状态链路；验证 UE UI 和报告时优先使用 UE 目标入口。

## 7. 自动场景与报告

输入文件为 [warehouse_baseline.json](../Config/Scenarios/warehouse_baseline.json)。关卡内放置 `ScenarioRunner`，机器人 Actor Tag 与 JSON 的 `actor_tag` 一致，`ScenarioFileName` 指向对应 JSON。

当前 Runner 在 `BeginPlay` 加载配置、设置起点和 LiDAR 并发送一次目标，没有完整的外部服务就绪等待与重发机制。因此上面的顺序先用于恢复手动导航链路；冷启动时 Runner 可能先于 Nav2 / Bridge 发送目标，不能把这种失败当成导航算法失败。自动化启动协调仍列在待办中。

单轮结果保存在 Windows 项目：

```text
Saved/ScenarioResults/*.json
```

检查 `scenario_id`、`run_id`、`state`、`task_ended_confirmed`、`detail`、`elapsed_seconds`。报告耗时是接受后的仿真时间；当前不包含完整碰撞评价，`Succeeded` 不代表已证明无接触。

## 8. 停止与重新启动

先在各终端 `Ctrl+C` 停止 Nav2、Bridge、RViz 和诊断，再停止并重新 Play UE，重新检查 Topic 后启动 ROS 进程。

UE 重新 Play 会重置仿真时钟，旧 ROS 进程可能保留上一轮 TF / costmap。出现 `TF_OLD_DATA` 或时间回跳时，先按此顺序清理旧运行状态。
