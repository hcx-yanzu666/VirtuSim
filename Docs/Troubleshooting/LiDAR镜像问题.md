# LiDAR 扫描镜像缺陷排查记录

> 记录一次"UE 机器人反复横跳穿过障碍物"问题的完整排查过程。
> 排查环境：Ubuntu 22.04 + ROS 2 Humble + Nav2，UE 5.6 运行在 Windows 侧，跨主机 DDS 通信。
> 结论：UE 侧 LiDAR 射线方向的 Y 轴手性错误，一行代码修复。

---

## 一、现象

UE 场景中放置了一个 Actor 作为静态障碍物。机器人执行导航任务时，行为在两个状态之间**反复横跳**：

- **状态 A**：完全没有识别到障碍物，机器人直接穿模通过
- **状态 B**：接近障碍物时识别到了，规划器绕行

同一个障碍物、同一条路线，两种行为交替出现，没有稳定规律。伴随的现象：

- RViz2 中 costmap 上的障碍物时有时无
- 规划器频繁报 `Failed to create plan with tolerance 0.50`
- 控制器频繁报 `Failed to make progress`，机器人走走停停
- 偶尔出现"目标点不可达"，但目标点看上去明明是空地

### 关键量化特征（来自诊断脚本日志）

```
[摘要] run=1 status=Navigating Hz(scan/odom/cmd/plan)=9.9/29.4/20.4/0.0
       scan_valid=94% scan_min=1.23m path=20.25m cmd=(0.00,0.68)
       costmap_lethal(local/global)=2177/52353
```

最刺眼的一条：

```
scan_min 最低到 0.39 m，而 robot_radius = 0.45
```

**激光测到了 0.39 m 处的东西，意味着障碍物已经在车体内部了。** 这排除了"完全没检测到"，把问题锁定在**间歇性检测**上。

`path` 在两个值域之间振荡，这是横跳最直接的指纹：

```
7.53 → 20.94 → 7.33 → 13.18 → 7.09 → 28.95 → 18.35 → 32.43 → 7.17 → 28.91 ...
```

只有两种路径长度在交替：一条**短的（约 7 m，直接穿过去）**和一条**长的（19~32 m，绕行）**。

`path_changes = 41 / 68 次规划` —— **60% 的规划结果都在翻面。**

---

## 二、系统分层

排查前先明确每一层由谁负责，避免在错误的层里找问题：

| 层 | 组件 | 责任 |
|---|---|---|
| UE 场景 | WarehouseSceneActor | 提供静态几何、碰撞体 |
| UE 传感器 | LidarComponent | Raycast 生成距离数组 |
| UE 消息转换 | LidarScanConverters | 厘米→米、度→弧度 |
| UE 通信 | RosCommunicationSubsystem + TempoROS | 发布 /scan、/odom、/clock、TF |
| ROS 通信 | DDS（跨主机） | QoS 匹配、传输 |
| ROS 定位 | AMCL | map→odom 修正 |
| ROS 建图 | costmap_2d obstacle_layer | 扫描→栅格标记/清除 |
| ROS 规划 | NavFn + DWB | 全局/局部路径 |

排查策略：**从下游往上，每层都用可观测量做判定，不靠推断。**

---

## 三、排查路线与结果

共 7 条路线。前 4 条被证伪后排除，第 5~7 条才收敛到根因。

### 路线 1：检查 Nav2 是否在正常运行

**假设**：节点挂了或 lifecycle 未激活。

**方法**：`ps`、`ros2 lifecycle get`。

**结果**：❌ **排除**。`controller_server` / `planner_server` / `amcl` 全部 `active [3]`，节点健康。

---

### 路线 2：检查仿真时钟是否冻结

**假设**：`use_sim_time: True` 全线打开，如果 UE 的 `/clock` 停发或跳变，sim time 冻结会让 costmap 卡在错误状态。

**方法**：`ros2 topic hz /clock`、连续采样 sim 时间增量。

**结果**：❌ **排除**。45 秒内 134 条消息，增量恒定 0.3333 s，**零跳变、零倒流**，sim/wall 比值 1.0025。时钟健康。

**翻车记录**：第一次观察到 `/clock` 11 秒零输出，误判为"时钟冻结"。实际上那时 UE 未连接。

---

### 路线 3：检查 QoS 兼容性

**假设**：TempoROS 发布者用 RELIABLE，Nav2 obstacle_layer 订阅用 SensorDataQoS（BEST_EFFORT），QoS 不匹配会导致 DDS 静默不投递。

**方法**：`ros2 topic info -v /scan`，对比发布者与订阅者 QoS。

**结果**：❌ **排除**。发布者确实是 `RELIABLE / TRANSIENT_LOCAL`，但用 BEST_EFFORT 订阅实测**能收到全部 361 个点**。QoS 兼容（RELIABLE 发布者可被 BEST_EFFORT 订阅者接受）。

---

### 路线 4：检查 TF 可用性

**假设**：扫描的时间戳比 TF 新，costmap 查不到那一刻的 `odom→base_link`，观测被静默丢弃。

**方法**：用 `tf2_ros.Buffer` 在每一帧扫描的精确时间戳上做 `lookup_transform`。

**结果**：❌ **排除**。非阻塞方式重测后 **127/127 全部成功**。

**翻车记录（重要）**：第一次测试报告大量 `ExtrapolationException: Lookup would require extrapolation into the future`，看起来是铁证。实际是**我的测试脚本在回调里调用了 `time.sleep()`**，阻塞了 executor，导致 `TransformListener` 根本没机会把 TF 写进 buffer。这是自造假象。

同时验证了扫描与 TF 时间戳的**精确交集是 68/68** —— 两者由同一个 3 Hz 定时器发布，时间戳逐位相同。

**方法论教训**：测量工具本身会改变被测对象。先怀疑测量，再怀疑系统。

---

### 路线 5：检查坐标原点是否偏移

**假设**：UE 世界坐标原点与地图原点不一致，扫描标记落在图外被裁掉。

**方法**：dump 静态地图、全局 costmap、局部 costmap 三张栅格，对比 origin 与 lethal 格分布。

**结果**：部分相关，但**不是根因**。

- 三者 origin 完全一致 `(-12.0, -8.0)`，分辨率 0.05，尺寸 480×320
- 局部 costmap 中心 `(8.50, -6.65)` 与机器人位置 `(8.5, -6.7)` 一致 → 滚动窗口正确
- 机器人在静态图中 cell=(409,25)，值为 0（自由），**在范围内，离边界余量充足**

**但发现了一个异常量**：全局 costmap 有 66679 格 lethal，而静态地图只有 17535 格 —— **49144 格"幻影"**。渲染出来是：

```
真实货架（静态图）:  实心 ####
幻影 lethal:        空心描边 ##..##
```

**这是本次横跳留下的"伤疤"** —— 镜像扫描被标进地图后又部分清除，留下描边残影。当时误判为"costmap 冻结"，实际是机器人静止导致静态层不变。

---

### 路线 6：检查扫描数据本身的质量

**假设**：UE 侧 Raycast 在丢点或返回假数据。

**方法**：dump `LaserScan.ranges` 原始值、统计不同取值数、画距离直方图；审查 `LidarComponent.cpp` 的射线逻辑。

**结果**：❌ **排除**。数据质量良好：

- 361 点，247 个不同取值，`NaN/Inf = 0`
- 原始值是平滑连续曲线：`7.34 6.73 6.62 6.65 6.68 6.71 6.74 6.78 6.82`
- `LineTraceSingleByChannel` 逻辑正常，`range_min/max` 填充正确

注意 `max = 10.00` 恰好等于 `range_max`，说明多数射线打空 —— 这是空旷场景的正常表现，但也是后来的线索之一。

---

### 路线 7（决定性）：把扫描点变换到地图坐标系，与 PGM 逐点比对

**假设**：扫描数据"看起来正常"，但**几何上不对**——打在了错误的位置。

**方法**：把每一帧扫描的每个命中点，经 `map←laser_link` 变换到地图坐标系，查 PGM 对应像素，统计"落在障碍上"与"落在地图外"的比例。

这是一个**独立于 ROS 链路的几何自洽性检验**：机器人在地图里，它看到的真实几何不可能落在地图边界之外。

**结果**：✅ **命中。**

| 变换约定 | 地图内 | 地图外 | 落在障碍 | 落在空地 | 障碍命中率 |
|---|---:|---:|---:|---:|---:|
| `+a`（当前实现） | 198 | **107** | 17 | 181 | **5.6%** |
| **`-a`（角度取反）** | **305** | **0** | **225** | 80 | **73.8%** |
| 翻转 y | 223 | 82 | 49 | 174 | 16.1% |
| `-a` 且翻转 y | 220 | 85 | 39 | 181 | 12.8% |

**107 个命中点落在地图外**，这是物理上不可能的。角度取反后：

- 地图外点数 **107 → 0**
- 障碍命中率 **5.6% → 73.8%**

两条独立指标同时自洽，假设成立。

---

## 四、根因

### 代码位置

`Source/VirtuSim/Robot/LidarComponent.cpp` 第 111–115 行：

```cpp
FVector LocalDirection(
    FMath::Cos(Angle),
    FMath::Sin(Angle),   // ← 缺陷在这里
    0.0f
);
```

### 原理

- **ROS 约定**：`LaserScan.ranges[i]` 对应的角度为 `angle_min + i * angle_increment`，**逆时针为正**（右手系，Z 轴朝上时逆时针增加）
- **UE 约定**：世界坐标系是**左手系**，Z 轴朝上时 Y 轴方向与 ROS 相反

于是在 UE 中按 `(cos θ, +sin θ)` 生成的射线序列，在 ROS 侧被解释为逆时针排列，实际打出去的却是顺时针排列 —— **整张扫描沿机器人正前方做了镜像**。

### 为什么表现为"反复横跳"而不是"稳定错误"

镜像后的环境是左右颠倒的：

- 机器人**左边**有货架 → costmap 标到**右边**
- 机器人**右边**是空的 → costmap 认为**左边是空的**

于是：

1. 规划器看到一条"绕开虚构障碍、穿过真实障碍"的路径
2. 真实障碍在镜像图中**可能恰好落在空地格** → 规划器**根本不认为那里有东西 → 直接穿过去**
3. 换个位置/朝向，镜像错位后同一障碍**落在障碍格** → 看起来"识别到了并绕行"

**同一个根因的两种表现。** 是否触发取决于机器人当前朝向与障碍物的相对几何关系。

### 附带影响

- **AMCL** 长期无法收敛：likelihood field 用整张镜像扫描做匹配，永远匹配不上真实地图
- **幻影 lethal 残影**（49144 格）：历史错误标记未被清除
- **规划器**频繁 abort：目标点常落入镜像制造的虚假障碍中

### 修复

```cpp
FVector LocalDirection(
    FMath::Cos(Angle),
    -FMath::Sin(Angle),   // UE 左手系：取反使角度递增方向与 ROS 逆时针约定一致
    0.0f
);
```

**只改这一处。** 后续的 `TransformVectorNoScale`、距离计算、单位换算全部不变。

## 六、残留问题

以下问题**不是横跳的原因**，但会影响稳定性，记录备查。

### 6.1 扫描时间戳系统性落后 TF 一个周期

```
clock = 882.682
scan  = 882.349  (-0.333)
odom  = 882.349  (-0.333)
TF    = 882.349  (-0.333)
```

**成因**：`/clock` 由 TempoROS 的 `OnWorldPreActorTick` 每帧发布；`/scan` 与 `/odom` 走各自 3 Hz 定时器。两者存在最大一个周期的错位。

**影响**：costmap 偶尔丢帧，日志可见：

```
Message Filter dropping message: frame 'laser_link' at time 779.672
  for reason 'the timestamp on the message is earlier than all the data in the transform cache'
```

丢帧率低，不影响导航结果。

**可选处理**：让 `/scan`、`/odom` 的时间戳取"当前仿真时刻"而非"上次 Tick 时刻"；或评估在本项目中关闭 `use_sim_time`（UE 没有统一仿真时钟源，用 realtime 反而更自洽）。

### 6.2 传感器频率偏低

`LidarParameters.h` 中 `ScanFrequencyHz` 默认 10.0，实测只有 **3 Hz**。以 0.26 m/s 行进时，两次扫描间机器人移动 8.7 cm，对 0.05 m 分辨率的 costmap 偏粗。需检查 UE 侧实际配置值。

### 6.3 TF 所有权冲突

`map→odom` 有两个发布者：

- UE 侧 `RosCommunicationSubsystem::PublishMapStaticTransform()` 发**单位变换**
- AMCL 发定位修正（`tf_broadcast` 需为 `True`）

参数文件中 `tf_broadcast` 原为 **`False`**，导致 AMCL 即使算出修正也不发布，而 UE 的单位变换掩盖了定位漂移。

**处理原则：只保留一个发布者。** 二选一：

- 保留 AMCL → 移除 UE 的 `PublishMapStaticTransform()`
- 走纯 odom 积分 → 关闭 AMCL

### 6.4 costmap 中的历史幻影

全局 costmap 中存在 49144 格不在静态地图中的 lethal，其中包含一轮地图边框环和货架描边。这是缺陷期间的扫描残留。重启 Nav2 后应从静态地图重建，需确认已清除。

---

## 七、方法论总结

1. **分层排查，每层用可观测量判定**：不从"哪里可能出错"出发，而从"这一层的数据能否自洽"出发。
2. **先怀疑测量工具，再怀疑系统**：TF 测试和时钟测试各翻车一次，两次都是测试脚本自身缺陷（阻塞 executor、UE 未连接）造成的假象，而非系统问题。
3. **找独立于被测链路的检验**："扫描点落在地图外"这个判据不依赖 ROS 的任何一层，只依赖几何，因此可信度最高。
4. **用自洽性而非正确性做判据**：无法直接知道"正确扫描长什么样"，但知道"命中点不可能在地图外"，后者足以定位问题。
5. **修复前后用同一指标对比**：5.6% → 86.5% 是可复现的量化证据，比"感觉好了"可靠。

## 八、面试话术

### 8.1 能不能说？—— 能，而且这是一个高质量的素材

**推荐说。** 理由：

- 问题有明确的**现象 → 假设 → 验证 → 根因 → 修复 → 回归**完整链路
- 根因是**一行代码**，但定位过程跨越 UE 渲染、Raycast、坐标变换、ROS 通信、Nav2 建图五层，体现系统级排查能力
- 有**可复现的量化指标**（5.6% → 86.5%）
- 涉及**坐标系手性**这类机器人领域真正容易踩、且很多人讲不清楚的坑

### 8.2 怎么说 —— 建议的表达方式

关键原则：**讲排查思路，不讲流水账；讲判据，不讲猜测。**

不要按"我先看了 A 不对，又看了 B 不对…"平铺直叙，那会显得像碰运气。按下面的结构讲：

---

> **【问题现象】**
> 我在做 UE5 + ROS2 + Nav2 的机器人闭环仿真。UE 侧场景里放了一个静态障碍物 Actor，机器人导航时行为会在两个状态之间反复横跳——有时完全看不见障碍物直接穿过去，有时又能识别并绕行。同一个障碍、同一条路，没有稳定规律。
>
> 量化下来有两个特征：一是 costmap 上的障碍物时有时无，规划出的路径长度在 7 米和 30 米之间翻，68 次规划里有 41 次翻面；二是激光测到的最小距离到了 0.39 米，而机器人半径是 0.45 米——也就是障碍物已经进到车体内部了。
>
> **【这一步是关键】**
> 第二条把问题的范围一下收窄了：它不是"传感器没检测到"，而是"检测到了但没起作用，或者作用得不对"。所以我不再往传感器能力上找，转去找数据流在哪里断掉或者被曲解。
>
> **【排查思路】**
> 我按数据流从下游往上分层验证，每层都找一个客观判据：
>
> - **通信层**：QoS 兼容性、DDS 是否投递 —— 实测能收到全部 361 个点，排除
> - **时间层**：仿真时钟是否冻结、时间戳是否对齐 —— 时钟增量恒定、零跳变，扫描与 TF 时间戳精确交集 68/68，排除
> - **变换层**：TF 在扫描时间戳上是否可查 —— 127 帧全部成功，排除
> - **数据层**：原始 ranges 是否被丢点或噪声污染 —— 247 个不同取值、曲线平滑，数据本身干净
>
> 四层全部干净，这说明**数据在正确的时间、以正确的格式、被正确地接收了，但内容是错的**。
>
> 【这里如果面试官追问，可以展开：中途我有两次误判——一次怀疑时钟冻结，一次怀疑 TF 外插失败，后来发现都是我自己测试脚本的缺陷造成的假象，前者是在回调里 sleep 阻塞了 executor，后者是测试时 UE 根本没连上。这让我形成一个习惯：先怀疑测量工具，再怀疑系统。】
>
> **【决定性的一步】**
> 既然链路全是好的，我就换了个思路：设计一个**独立于整条 ROS 链路的几何自洽性检验**——把每一帧扫描的每个命中点，经 TF 变换到地图坐标系，直接查栅格地图对应位置是障碍还是空地。
>
> 这个检验的好处是：它不需要知道"正确的扫描长什么样"，只依赖一个几何常识——**机器人在地图里，它看到的真实几何不可能落在地图边界之外**。
>
> 结果：198 个命中点里只有 17 个落在障碍上（5.6%），而且**有 107 个点落在了地图外面**。
>
> 然后我做了对照实验，同时试了四种角度约定：
>
> | 约定 | 地图外点数 | 障碍命中率 |
> |---|---:|---:|
> | 当前实现 | 107 | 5.6% |
> | 角度取反 | **0** | **73.8%** |
>
> 角度取反后两条独立指标同时自洽，问题锁定。
>
> **【根因】**
> UE 是左手坐标系，ROS 是右手坐标系，Z 轴朝上时 Y 轴方向相反。我的 LiDAR 射线方向用的是 `(cos θ, +sin θ)`，在 ROS 侧被解释成逆时针排列，实际发出去的却是顺时针——**整张扫描沿机器人正前方做了镜像**。
>
> 这解释了为什么是"横跳"而不是稳定错误：镜像后的环境左右颠倒，同一个真实障碍在镜像图里可能落在空地格，也可能落在障碍格，取决于机器人当前的朝向和相对位置。落在空地格时规划器认为那里没东西，直接穿过去；落在障碍格时才绕行。
>
> 修复就是一行：把 `sin` 取反。
>
> **【验证】**
> 修完用同一个指标回归：障碍命中率 5.6% → 86.5%，地图外点数 107 → 0，规划路径点数零跳变，costmap lethal 零跳变。最后从 (8.5, -6.7) 自主导航到 (-9.0, 6.0)，停在距离目标 0.205 米的位置。
>
> **【反思】**
> 这件事让我印象最深的是：前面四层验证全部"通过"，而问题恰恰是**通过得太干净了**。如果当时停在"链路没问题"就继续加日志、加打印，会一直在错误的层面打转。真正突破的是换了一个判据——从"数据能不能到"换成"数据几何上自不自洽"。

### 8.3 常见追问与应对

**Q：为什么一开始没怀疑坐标系？**

> 因为从日志看，扫描数据本身是"健康的"——361 个点、无 NaN、曲线平滑、时间戳对齐、TF 可查。这些信号都在说"数据没问题"。但"数据健康"和"数据正确"是两回事：我验证的都是**传输和格式的正确性**，没有验证**几何内容的正确性**。坐标系错误不会破坏任何一条前置检查，它只在几何层面暴露。

**Q：为什么是间歇性的？如果坐标系错了，不应该一直错吗？**

> 坐标系确实一直错，但**表现**不是一直穿模。镜像后的环境是左右颠倒的，一个真实障碍在镜像图里会落到哪个格子，取决于机器人当前朝向和障碍物的相对位置。有时落进空地，有时落进障碍，所以看起来时好时坏。这也解释了为什么这个问题特别难复现——它不是随机的，是几何相关的。

**Q：怎么保证你的修复是对的，而不是碰巧？**

> 两个层面。第一，修复前后用的是同一个独立指标——扫描点投影到地图坐标系后的障碍命中率，从 5.6% 涨到 86.5%，而且"地图外点数"从 107 降到 0，这是两条独立指标同时改善。第二，我做了对照实验，把四种可能的约定都试了一遍，只有角度取反这个假设能同时让两条指标自洽，其他三种都不行。

**Q：这个过程中有什么教训？**

> 有两次我给出了错误结论，都是我自己测试脚本的缺陷造成的：一次是我在 ROS 回调里调用 sleep 做轮询，阻塞了 executor，导致 TF 监听器根本没机会往 buffer 里写数据，于是"测出"大量外插失败；另一次是测试时 UE 侧其实没连上，我却把它读成了"时钟冻结"。这两次让我形成一个习惯：**拿到一个看起来很确凿的异常时，先花两分钟确认这个异常是不是自己造出来的。**

**Q：这个项目里你觉得最有技术含量的部分是什么？**

> 不是修复本身——修复是一行代码。有技术含量的是**定位过程**：在一个 UE + DDS + ROS2 + Nav2 的跨平台、跨主机的多进程系统里，把"机器人行为异常"这种模糊现象，转化成"扫描点投影后的障碍命中率"这种可测量的量，然后用它逐层排除。这个过程里最关键的判断是：当所有链路层检查都显示正常时，意识到要换一个**不同性质**的判据——从链路的连通性，换成几何的自洽性。

### 8.4 不建议的表述

| 不要说 | 为什么 |
|---|---|
| "查了三天最后发现是坐标系问题" | 显得只有苦劳没有方法，且暗示过程无结构 |
| "UE 的坐标系有 bug" | UE 没有 bug，是**你的代码**混用了两套约定。这个区分体现对系统边界的理解 |
| "改了 sin 的符号就好了" | 只讲结果不讲判据，面试官会怀疑是碰巧试出来的 |
| "我一开始就怀疑是坐标系" | 与事实不符，且面试官一追问细节就会露馅 |
| 只讲根因不讲排查路线 | 面试官想考的是**排障能力**，不是"你知不知道这个坑"。根因一行代码，排查能力才是区分度 |
